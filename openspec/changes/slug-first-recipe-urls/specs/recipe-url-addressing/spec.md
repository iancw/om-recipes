## ADDED Requirements

### Requirement: Homepage recipe deep links use slug-based canonical URLs
The homepage SHALL represent an opened recipe in the URL as `/?recipe=<slug>` and SHALL use the recipe slug when creating or updating browser history state for recipe modal navigation.

#### Scenario: Opening a recipe from the homepage uses the slug query parameter
- **WHEN** a user opens a recipe modal from the homepage
- **THEN** the browser URL contains a `recipe` query parameter whose value is the recipe slug

#### Scenario: Closing the recipe modal removes the canonical query parameter
- **WHEN** a user closes an open recipe modal on the homepage
- **THEN** the `recipe` query parameter is removed from the browser URL

### Requirement: Homepage deep links remain backward compatible with legacy identifiers
The homepage SHALL continue to accept legacy recipe deep-link query parameters and UUID values, and SHALL normalize any successfully resolved recipe deep link to the canonical `recipe=<slug>` form.

#### Scenario: Legacy query key still opens a recipe
- **WHEN** the homepage is loaded with `?id=<uuid>` for an existing recipe
- **THEN** the matching recipe modal opens once that recipe is available in the loaded result set

#### Scenario: Legacy deep link normalizes to canonical slug form
- **WHEN** the homepage is loaded with `?id=<uuid>` or `?uuid=<uuid>` or `?slug=<slug>` for an existing recipe
- **THEN** the browser URL is rewritten to use `?recipe=<slug>` without closing the modal

#### Scenario: Canonical key accepts UUID aliases for backward compatibility
- **WHEN** the homepage is loaded with `?recipe=<uuid>` for an existing recipe
- **THEN** the matching recipe modal opens and the browser URL is rewritten to `?recipe=<slug>`

### Requirement: Dedicated recipe pages use slug paths as the canonical URL
The app SHALL use `/recipes/<slug>` as the canonical dedicated recipe page URL while continuing to resolve UUID paths for backward compatibility.

#### Scenario: Slug path renders the recipe detail page
- **WHEN** a user requests `/recipes/<slug>` for an existing recipe
- **THEN** the app renders that recipe's detail page

#### Scenario: UUID path redirects to the slug path
- **WHEN** a user requests `/recipes/<uuid>` for an existing recipe
- **THEN** the app responds by redirecting the user to `/recipes/<slug>`

#### Scenario: Unknown identifier still returns not found
- **WHEN** a user requests `/recipes/<identifier>` that matches neither an existing recipe slug nor UUID
- **THEN** the app returns the existing not-found response

### Requirement: Generated recipe links use the canonical slug URL
Any user-facing recipe link generated by the app SHALL point to the canonical slug URL rather than a UUID-based URL.

#### Scenario: In-app recipe links use the slug path
- **WHEN** the app renders a link to a dedicated recipe page from the homepage, upload flow, related recipes, sample views, or camera slot views
- **THEN** the href is `/recipes/<slug>`

#### Scenario: Generated homepage share links use the slug query parameter
- **WHEN** the app renders or copies a homepage URL that opens a specific recipe modal
- **THEN** the URL uses `?recipe=<slug>`
